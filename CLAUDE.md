# CLAUDE.md

How to work on this repo. Overview: README.md; each subsystem README lists what it owns and its Requirement Spec sections.

## Project

A FAIRINO FR5 arm with a suction gripper picks whole catfish off a table and places them with a uniform heading. **Vision** (RealSense D405, YOLO26 segmentation + pose) finds each fish's pose; **ControlSys** runs the cycle (Qwen3-VL picks the fish, fixed code validates every answer and owns every limit); **Arm** moves (MoveIt 2 with Pilz, frcobot_ros2). Fall 2026 is the design term. Working code: the Vision data pipeline in `Vision/data/`, and a first pick-and-place cycle in the `rfp_*` packages (below) that runs in the 3D simulator and in tests but has not been on the real arm.

Requirement IDs (Requirement Spec, Confluence) use these prefixes in code, docstrings and commits: SY system, VS vision, VD vision data and models, CS control, AS arm, SF safety, IF interfaces, HW/SW platform, HC hardware constraints.

## Environment

- `setup.ps1` / `setup.sh` run `tools/setup_rfp.py` (standard library only: it runs before any environment exists): each step checked first, done only if missing (the conda env `rfp`, Python 3.10, matching ROS 2 Humble on Ubuntu 22.04; it asks pip with a dry run whether anything is missing). `--robot` (robot PC) also installs ROS 2, MoveIt 2, ros2_control, librealsense, dialout, clones frcobot_ros2 at FAIRINO's driver for the controller's firmware (`--firmware`, else read from the controller's port 8080 as FAIRINO's own dispatcher does; a tag per firmware, `FRCOBOT_COMMITS` for the untagged ones; from 3.9.6 the other firmwares' `fairino_hardware_v*` folders get COLCON_IGNORE: they export the same plugin) and builds it, with the Python environment a `.venv` on the system Python that sees rclpy. On the robot PC everything runs through `./robot.sh` (sources ROS, the workspace, `.venv`).
- **Python 3.10 code only** (no `tomllib`, `except*`, `typing.Self`, ...): the `rfp_*` packages run under ROS's Python.
- Dependencies go in the `pyproject.toml` extras (`vision`, `arm`, `control`, `analysis`, `dev`) **and** in `requirements.txt`, which lists every package explicitly (a test checks it covers every extra) and pins torch/torchvision to the CUDA index.
- ROS 2, MoveIt 2, frcobot_ros2, librealsense and vLLM are system installs on the robot PC. Label Studio needs its own environment (it pins `numpy<2`).
- Development is on Windows (VS Code, PowerShell or Git Bash); the robot PC runs Ubuntu. Keep code cross-platform: `pathlib`, no shell calls, tkinter for GUIs.

## Commands

- `pytest` from the repo root. GUI tests skip without a display, the RealSense test without pyrealsense2, SAM tests without the SAM weights (`RFP_SAM_WEIGHTS` points at a `sam2.1_t.pt`). `test_rfp_*.py` needs the repo installed (`pip install -e .`; the conda env does it). `pyproject.toml`'s `addopts` turns off ROS's pytest plugins (`launch_testing`, `launch_ros`, `ament_*`): with ROS sourced on the robot PC they broke the run.
- `ruff check .` and `ruff format .`: ruff pinned to 0.17.x (`dev` extra; default rules change between minor versions), line length 100 (E501). The pre-commit hook (rev must match the pin) runs both on commit; `.github/workflows/checks.yml` runs them and the light tests (dev extra only) on push.
- Every pipeline script supports `--help`; without arguments it asks for its inputs in popups.

## Vision data pipeline (`Vision/data/`)

| Step | Script | Writes |
|---|---|---|
| 1 | `preprocessing/extract_frames.py` | `dataset/image_sets/<video name>/` |
| 2 | `annotating/auto_labeler.py` (SAM or color engine) and/or Label Studio | `.txt` labels next to the images |
| 3 | `annotating/augment_images.py` (pixel-only effects) | `dataset/image_sets/<set> (augmented)/` |
| 4 | `annotating/label_viewer.py` | fixed labels; deleted pairs go to `<set>/_deleted/` |
| 5 | `preprocessing/train_val_data_splitter.py` | `dataset/train/` (train/val/test) and `data.yaml` |
| 6 | `training/train.py` (settings: `training/fish_seg.yaml`) | `Vision/trained_cv_models/<name>_<model>_<date>_<time>/` |
| Preview | `Vision/tests/model_viewer.py` | `Vision/tests/model_previews/<video> - <model>.mp4` (git-ignored) |

Rules the code depends on:

- **`pipeline_common.py` owns paths, file names, label I/O, image I/O and popups.** Use its helpers (`set_dirs`, `label_index`, `find_label`, `read_label`, `write_label`, `imread`, `imwrite`, `mask_to_polygon`, `ask_*`). The scripts aren't a package; each adds `Vision/data` to `sys.path`.
- **Labels** are YOLO segmentation polygons, normalized 0-1. `read_label` returns non-polygon lines separately (`other`); write them back unchanged. `write_label` cuts polygons at the image edge (`clip_polygon`, joining the crossing points along the edge): YOLO skips images whose labels go past 0-1.
- **Names carry meaning.** Frames: `<video name>_<frame number:06d>.jpg`; videos are named by fish ID and view (`fish012_left.mp4`). Augmented copies: `<original name>__aug<n>-<effect>`. Label Studio's `1a2b3c4d-` label prefix is matched.
- **The split** is 80/10/10 train/val/test (`TRAIN_RATIO`, `TEST_RATIO`), each set cut in blocks of consecutive frames so near-duplicate neighbors don't leak across splits; augmented images go to train only, when their original is in train. The same fish may be in every split (the team decided against splitting by fish, despite VD-70's wording). Keep the block and augmented rules.
- `Vision/data/dataset/classes.txt` is the class list (tracked); the splitter stops if a set's `classes.txt` disagrees.
- **Auto labeler** = `LabelViewer` (`annotating/label_viewer.py`) + click-to-label (`annotating/auto_labeler.py`, engines in `annotating/segmentors/`). The second toolbar row shows the current mode's tools (`edit_tools` / `auto_tools`). New outlines replace labels they overlap by IoU > `REPLACE_IOU`. SAM is freed on engine switch and close.
- **No data in Git.** `.gitignore` ignores `Vision/data/dataset/` except `.py`, `.gitkeep` and `classes.txt`, plus `Vision/trained_cv_models/*` except each run's `weights/best.pt` (tracked: the model the cell runs, ~55 MB each; GitHub warns past 50 MB and refuses past 100 MB), `Vision/data/training/mlflow/` and other `*.pt`. The newest run is found by the date in its name, not file times (a clone's are all the same).
- End-to-end checks: copy `Vision/` to a temp folder and run the scripts there (paths are relative to `pipeline_common.py`, so real data stays untouched).

## Pick and place (`rfp_vision`, `rfp_arm`, `rfp_controlsys`)

`ControlSys/rfp_controlsys/pick_place.py --mode setup | sim3d | sim | check | dry-run | run` (in bring-up order; `check` is everything that moves nothing: camera, fish, the arm's driver, state and force, the camera alone without ROS; `dry-run` and `run` calibrate the camera first while it isn't) (its docstring explains each; `main.py` at the root runs it, `./robot.sh` on the robot PC). Rules the code depends on:

- **Three layers behind interfaces.** `rfp_controlsys.cycle` talks to an `Arm` and a `Gripper` (`rfp_arm/interfaces.py`), a `VisionSystem` and a `FishSelector`. Modes only swap what is behind them (`SimArm`/`MoveItArm`, `SimGripper`/`NoGripper`/the real gripper from `make_gripper`). `rfp_vision` and `rfp_arm` don't import each other; `rfp_controlsys` imports both.
- **ROS only in `moveit_arm.py`, `fairino.py`, `ros_link.py`**, imported inside functions: every other module must import and run without ROS (Windows, CI).
- **Units:** meters and radians in code, 4x4 poses `T_a_b` (frame b in frame a), {B} = MoveIt's `base_link`. YAML files use meters and degrees, logs mm and degrees (IF-11).
- **Point-to-point moves go to joint goals** from the robot model's IK seeded with the present joints (`Chain.ik`; a long swing that one solve can't reach is solved in steps about the base; a solution on the other side of the base is refused, `Chain.ahead`: near the base the posture folded back over it is nearer in joint angles, a solve took it, and from then on the gripper ran into the forearm over fish near the base), so the arm keeps its posture and the wrist ends where `Arm.wrist_angle` predicted; MoveIt's own IK (a pose goal) is only the fallback.
- **Every plan is checked in fixed code before it runs** (`safety.check_trajectory`: the speed of every point of the arm, each link origin, the TCP and the camera, against `tcp_speed_max`; zones, joint travel, the arm against itself), every target by `Workcell.pose_problem`, and the whole grasp plan before anything moves (`grasp.plan_problem`: each pose solved from the last, starting at the arm's joints, the arm against itself in each; a refused plan moves nothing and pauses nothing, so no pick is begun that would stop half way with a fish on the cups). A plan that moves the arm in no time (two points, one time: a jump past any speed limit) is refused (`safety.JUMP`). Don't add a motion path that skips them. Plans that are only too fast are planned again slower (PTP and LIN in `moveit_arm.py`; the simulated arm paces by the same points, `VirtualArm._paced`).
- **Bring-up** (`Arm/ros/fr5_bringup.launch.py`): FAIRINO's MoveIt config through `moveit_configs_utils` with the hardware plugin asked for swapped in for ros2_control_node only, whichever of mock and real their xacro names (`swap_plugin`: string replace of the processed xacro; their files untouched), `Arm/ros/joint_limits.yaml` (their 0.7 rad/s2 accelerations made every move take seconds), Pilz's sequence capability (the `capabilities` key alone: replacing the whole setting dropped `disable_capabilities` and move_group stopped), the launch shut down when ros2_control_node dies, and the command server with the real arm started once every controller spawner has exited (`after_all`: a 3.7 controller takes one SDK connection, which the driver needs first). A launch a mode started is waited for (`pick_place.wait_for_launch`): if it dies on the way up, the run stops with its first `[ERROR]` line and a hint (FAIRINO's packages not sourced; the driver's connection failed). `rfp_arm/bringup.py` starts it from a ROS mode when nothing publishes `joint_states` (`run.bringup`), stops it at the end. It can't run here: test changes with `./robot.sh ros hardware:=mock` on the robot PC. `robot.sh` sources ROS, the `source .../setup.bash` lines of `~/.bashrc` (a script doesn't read it) and the first workspace with `fairino_hardware` built (`$RFP_WS`, `~/rfp_ws`, any folder in the home; a test runs its functions in bash). Real modes refuse a MoveIt whose joints aren't the controller's (`same_arm`: FAIRINO's demo launch with mock hardware left running) and a driver built for other firmware (`check_driver`: setup writes `.rfp_firmware` in the workspace).
- **FAIRINO firmware** (`fairino.py`): 3.7.x drivers publish `error_code`, 3.8.2+ `main_error_code`/`sub_error_code` (read with `error_code()`); the 3.7.5 driver (no `abnormal_stop` in its state) answers `1` for success, 3.7.6+ `0` (`succeeded`, `execute`); outputs are confirmed from the state; the newest dispatcher publishes `reconnect_flag` 1/2 while it has no driver for the firmware (a fault; its states are zeros, which `FairinoIO._measured` doesn't read as joints or torques: taken for the arm's joints they blamed MoveIt). On the real 3.7 controller the command server sent no state at all: `connect` names the causes (a driver for other firmware, the controller unreachable, a second command server: `bring_up` starts none beside one already running, found by its service), and real modes go on `stateless` (`connect(require_state=False)`: the generation from whether it answers `GetRobotVersion()`, outputs judged by the answer, no faults or torques read here; the controller still stops the arm). `Arm/tests/fairino_states.json` holds the 3.7.5 and 3.7.8 state messages for the fake (`FakeRobot(firmware=...)`). Manual mode (`robot_mode` 1) is a fault: the driver moves nothing then. `make_ready()` sends `ResetAllError()`, `Mode(0)` (automatic), `RobotEnable(1)` (nothing moves; both driver generations parse them; with the state, the state says whether it worked, else the answers); dry-run and run ask first (`pick_place.ready_controller`; `-y`: yes), never for a pressed emergency stop; stateless they can't tell, so they ask every time and a no goes on (in manual mode the driver just doesn't move the arm).
- **Blended moves:** `MoveItArm.move_through` plans LIN items with Pilz's `/plan_sequence_path` (only the first item has a start state, the last blend radius is 0, each radius under half of either segment: `BLEND_ROOM`), checks the joined trajectory, runs it; it returns False with nothing moved when it can't, and `GraspSequence._blended` then moves one at a time (lift, carry with its PTP fallback, lower). `_joined` sets each time in whole nanoseconds (a fraction rounding up to 1e9 ns is no Duration). The 3D simulator's `VirtualArm.move_through` blends the same way (`rounded_path`: corners rounded within the same radii, the whole path planned and checked first, timed from rest to rest over its length); one move at a time it stopped at every waypoint of a carry. The cycle tests' `SimArm` moves one at a time. While a blended move runs, the step (lift, carry, lower) follows the TCP's nearest segment.
- **The arm against itself** (`rfp_arm/collision.py`): the FR5's links and the gripper as built as spheres (`Arm/configs/collision_model.yaml`, `tool.collision_model`; `""` turns it off), checked along every planned path and in `layout.reach_joints` (a pose reached only against itself is out of reach). Every point of each mesh is in a sphere, none reaches more than its margin past the body (1 cm; 7 mm for the forearm and wrist 2, which are 19 mm apart wherever the tool points down). `Simulation/make_collision_model.py` makes it from the meshes (it needs FAIRINO's, and pyvista): run it again after changing the gripper (a test checks its hash). Not checked against each other: neighbors at a joint, and pairs whose meshes never came within 1 cm in 20000 random poses (MoveIt's "never in collision"). A path is checked every 1 cm of the way (`collision.STEP`), not only at the plan's own points (Pilz samples every 0.1 s: a few cm at the gripper); a pair touching where a path starts may come apart, not touch again. MoveIt's scene has the gripper as one box (`tool.body`); this check runs on every planned path, the 3D simulator's too (the cycle tests' `SimArm` plans no joints). A held fish isn't in it.
- **The VLM goes in as a `FishSelector`** (`selector.py`); its answers pass `validate_decision` and the fallback rule already. Don't let a selector reach the arm any other way (CS-30).
- **Each setting is written in one place.** Defaults live only in the settings dataclasses (`VisionSettings`, `ControlSettings`, `SimSettings`, `MotionLimits`/`GraspSettings`/`GripperSettings`, `WRIST_RANGE_DEG`), with their explanations; there are no YAML copies of them. `Arm/configs/workcell.yaml` holds only the cell as measured (frames, tool, camera mount, zones, poses, slots). `control_panel.yaml` (repo root) is where values are changed: it goes on top for everything that loads settings (`load_workcell`, the three `load_settings`; `panel=None`: the defaults alone, which tests use, so tuning the panel doesn't change them). A key may be in the panel or in workcell.yaml, not both (a test checks). Its `run` section holds `pick_place.py`'s command-line defaults. Unknown names are errors. `--vision`/`--control` take an extra settings file. The cell is unverified until the panel says `verified: true`: the real arm refuses it.
- **Slots are used in turn, round and round** (`PickPlaceCycle._slot`): a placed fish is taken away (by hand, or a conveyor) before its slot comes round again, so one slot is enough and the run never pauses for a full placement zone. The cycle forgets a placed fish when its slot is used again (`_placed`, for carry heights); it can't see the slot, so it trusts that. The simulator takes placed fish away once the next is on the cups (`World.take_away_placed`: hidden, nothing to touch; the benchmark scores where each lay).
- **Benchmark a change to vision, planning or the cycle** before and after: `python Simulation/benchmark.py [--compare <earlier run>]` runs the real cycle on seeded scenes (stand-ins of the simulation's `fish_length`, 0.60 m like the real fish, lying anywhere; `--fish-length 0.79` for the big prints) and scores it against the simulator's truth (`rfp_sim/benchmark.py`). Give each new behavior a setting that turns it off, so the comparison differs by that alone. A scene's layout and camera noise come from its seed alone. One fish per scene only ever fills slot 1: use `--fish 2` for anything about placing.
- **The cell's turn:** the layout is written in the cell's frame, turned `cell_yaw_deg` about the base from {B} (`Workcell.cell_yaw`): zones are `Rect`/`Box` ranges with that `yaw` (`local`, `base`, `corners`, `contains`; `turn_xy`), slots, `camera_xy` poses and the heading are turned on loading, taught `joints_deg` poses aren't (taught where the table is). Code that needs a zone in {B} goes through those, never its bare ranges. The setup editor keeps the layout in the cell's frame and draws it turned; **Face the arm** sets the yaw so the pick area's middle lies where the real arm's TCP points (`pick_place.arm_joints_reader`: `/joint_states` through `RosLink.joint_reader`, a message newer than the click). As set on the robot PC (−75: 75 deg clockwise), the pick area lies across the back of the arm.
- **The layout** (`rfp_arm/layout.py`; `--mode setup` is its 3D editor, `rfp_sim/layout_editor.py`): `check_layout` checks a workcell against what the FR5 model reaches (IK seeded facing each target, elbow up, j6 inside the tube's range, the arm clear of itself; observation poses, the pick area at a fish's top and at the lift height, each slot at the carry and release heights), the arm's links and gripper against the keep-out zones in those poses (`CollisionModel.in_box`: reaching near, the elbow comes back over the base; along paths only MoveIt checks them), the first joint between a look, a fish and the slot (`_first_joint_turns`: j1 stops at ±175 deg, so across the back of the arm they are on both sides of the stop, the arm would turn the long way round, more than `max_joint_travel_deg`; each place is reachable on its own, and the benchmark placed none of 20 fish), the camera's views (a fish lying where no view sees any of it) and the fish's ends (off the table, into a keep-out zone). Every mode prints it at the start. `save_layout` writes only the layout's lines, in the control panel where it overrides the file (the heading), keeps `.bak` copies, refuses a layout with `problems()` or one it can't write line by line, reads the files back (anything else changed: restored), and sets a verified cell unverified. The editor is kept to what a person sets by hand: the corners of the table, pick area and placement zone, the slots, where keep-out zones are (a ball each; one along a whole table edge, the operator's side, goes along the edge nearest the ball and follows the table as it is sized), quarter turns; the camera's views follow the pick area, the placement zone grows to hold its slots, an added slot goes where a whole fish fits (`free_spot`), and hints about the heading (`Finding.minor`) are printed, not shown. VTK drags a sphere widget parallel to the screen at about the focal point's depth, not the ball's, so a ball trails the mouse (up to 10%): the editor puts each ball where the mouse is on the table (`_under_mouse`).
- **Fish types** (`vision.fish_type`: `stand_in` or `catfish`) hold the size ranges and `balance_ahead_share`: the head is heavier, so the cups go that share of the measured length ahead of the outline's middle, toward the head (only with the head end known; the panel sets 0.05 for stand-ins, as the user set it on the robot PC; they balance at 0.126). `Fish.middle` (`target_pose`) is what the pick area and the slots are about, `Fish.grasp_point` where the cups go; `plan_grasp(..., middle=)` puts the middle on the slot, and `GraspPlan.middle_x` tells the arm (`set_held_fish(length, middle_x)`) so the safety checks put a held fish's ends around its middle, not the cups.
- **Finding fish** (`cycle.py`): a search looks from the observation poses in turn (`search_frames`) until one sees a fish; every fish seen is a `Sighting` (compared by identity: it holds arrays), matched look to look within `SAME_WHOLE` (seen whole both times), `SAME_CUT`, then `FOCUS_MATCH` for what is left (a cut-off fish's estimated middle drifts: matched any tighter, a search re-created exhausted fish forever). A focus looks from straight above the fish, just high enough for `look_margin` times its expected length (`_look_poses`: lower ones and the other way round after, in case the arm can't reach), between `_look_floor` (the cups `pregrasp_distance` over the tallest fish of its type) and `_look_ceiling` (close_height), not from the search's height: the grasp goes by this look's depth, and the D405's noise grows with the square of the distance (the robot PC searches from 0.65 m; in the simulated cell the grasps were measured from 0.51 m (median; 0.61 m after a first look that cut the fish off), about 40% less noise; `look_margin` 1.25: at 1.15 more first looks cut the fish off). Again while it is cut off: its middle from `Fish.estimate` (the end that shows plus half the expected length), its length at least the view that didn't fit, so each look goes higher; from the highest look, aimed where it was (`STILL_AIMED`), it isn't looked at again: the look would be the same. `max_looks_per_fish` looks without a candidate set it aside; a reason from a look that saw all of it isn't replaced by one from afar. All set aside, or `MAX_IDLE` cycles without a grasp: the operator is told why. The re-check before a grasp (CS-41) is taken only when the decision took `recheck_after_s` or longer (`>=`: Windows' clock ticks in ~16 ms), timed by the selector alone: timed from the frame, vision's own time counted, and two benchmarks run side by side took extra looks and placed different fish. A whole fish jumping by more than `max_jump_m` and the camera's move between two looks stops the run (`_check_mount`: a camera turned 60 deg or more on its mount; at half the move, two long fish lying close, one taken for the other, stopped a benchmark run), unless another fish lies near where it was expected (`_alone`). What a look sees where the arm's own body lies between the camera and the table (`CollisionModel.over`, the tool's link left out) isn't remembered: looking near the base, the detector took the shoulder for a fish cut off at the edge, which no look reached and which ended a finished run with an alert.
- **Carry height:** `plan_grasp(..., clear_z=)` carries the fish its height plus `droop_share` of its length plus `lift_margin` over the highest thing near the way it goes (straight, or by way of a turning spot: `_clear_height(way=)`, planned again higher if the detour passes over a fish) (`PickPlaceCycle._clear_height`: fish seen, fish placed; within half a fish and `carry_corridor_m`), at most `lift_height_max`; `carry_over_seen: false` gives the old fixed height. The layout check still uses the fixed height (the worst case).
- **Calibration** (`calibrate.py`; a `dry-run` or `run` with `camera.calibrated: false`, or with `--calibrate`, runs it first from the first observation pose, `pick_place.calibrate_first`, and saves `calibrated: true` with the mount; there is no mode for it alone): the object followed from look to look is the one nearest the image's middle at the start, then nearest where it was (with several fish in view the first detection switched between them); translations give the mount's rotation (Kabsch; a reflection fits best: the image is mirrored), turns and tilts about the TCP the lens's x and y; z (along the tool) stays the workcell's: tilts move the object's apparent middle, which made z 4 cm off in the simulator. `save_mount` writes the `mount:` and `calibration_version:` lines only.
- **3D twin** (`rfp_sim/twin.py`): the camera's view as a pyramid down to the table (`render.view_pyramid`, as in sim3d; the setting's lens until the first frame, then the camera's own intrinsics); follows `arm.joints()` from the console's `on_show` hook (VTK in the cycle's thread), shows each fish list from `PickPlaceCycle.on_fish_list` (`render.VisionLayer`: outlines, cups, heading, the depth as points colored by height); `run.twin` turns it off. sim3d's window draws the same layer over the true fish (`Viewer.show_fish`, `run_cycles(twin=)`): what vision measured against what is there.
- **The pick area's edge:** a fish whose middle vision puts within `PICK_AREA_TOLERANCE` (3 cm) past it counts as inside (`Workcell.in_pick_area`; vision gets `pick_area_seen`): one lying at the edge was measured 7 mm out and left, the operator asked about it. The plan's checks still decide whether it is picked.
- **Never into the table:** on the real arm the cups were pushed through a fish into the table until the arm lifted itself. The layers, each on its own: vision's top of a fish is the higher of its depth and `table.z` plus its height over the table measured around it (`FishLocator._top`: a wrong camera height or `table.z` stops the cups short, never deeper), and a top under `MIN_FISH_HEIGHT` (30 mm) above that table is `invalid_depth`; a table measured more than `table_tolerance_m` (15 mm) off `table.z` stops the run before the cups go down (`PickPlaceCycle._grasp`; vision takes a table within `table_search_m` of `table.z`, past that `table.z` and the other layers); the cups go at most `max_press` past the top (at most `MAX_PRESS_LIMIT`, under the bellows' 30 mm; `press_distance` may not be more); their lowest lip (`cycle.cup_rims`: the six cups' rims, tilted with the tool) stays `table_clearance` above the higher of `table.z` and the measured table (`GraspSequence._floor`, `_deepest`); the table the camera sees on the way down (`cycle.table_seen` of the newest frame, placed by the camera pose it was taken from: `_frame_camera`) stops the move where the lips come that close (`_too_low`, then E_NO_SEAL: the fish is tried again). `feel_contact` is off in the panel until `--mode check` shows the force rise; `--mode check` prints the touch-off (the cups' height over `table.z` and over the camera's table).
- **Refused plans:** `plan_grasp` refuses a fish where it lies (a fish end into a keep-out zone, the wrist past its range, the approach too steep). Nothing moved, so it counts toward the fish's attempts (vision may measure it otherwise next time) but not toward the cycles failed in a row that pause the run (CS-63): one awkward fish doesn't stop the others.
- **Taught demos** (`rfp_controlsys/demo.py`, files in `Demos/`): joint poses in degrees and `joints` / `line` / `vacuum` / `wait` steps, played through the same `Arm` and `Gripper`. A demo opens the workcell's zones (`demo_workcell`): its poses were reached on the arm when taught. Bare `on` / `off` in YAML are booleans.
- **3D simulation** (`Simulation/rfp_sim`, `--mode sim3d`, needs pyvista): a `VirtualArm`, `VirtualGripper` and `VirtualCamera` behind the real interfaces, so the real cycle and vision run on rendered color and depth. Its camera's image size and field of view are vision's (`VisionSettings.lens()`, passed as `lens`; tests pass a 320 x 180 one). It is to look like a real run: improve it toward run mode, never run mode toward it. Its moves are timed as Pilz times them on the arm (`devices.rest_to_rest`: speeding up and slowing down at the joint limits of `Arm/ros/joint_limits.yaml` (a test compares `JOINT_SPEEDS`, `JOINT_ACCELS`) times the ptp scales, straight moves at their speed and `tcp_accel_max`): at constant speed its short moves took a third of the time they take on the arm, and the empty arm looked much faster than it will be. The arm starts at the first observation pose in the posture the layout check assumes (`layout.reach_joints`: facing it, elbow up); picking the posture with j6 nearest 0 instead had it folded back over the base in the turned cell, where every carry wound the wrist into its stop. The fish model is `Simulation/models/catfish.3mf`, the gripper `Simulation/models/gripper.stl` (its CAD model through `Simulation/import_gripper.py`, in the tip link frame; both tracked, other models there are ignored). The gripper's measured TCP (`tool.tcp`), cup layout (`cup_rows`, `cup_columns`) and footprint (`cup_footprint_m`, 200 x 100 mm) must match the mesh: a test checks. The FR5's meshes are FAIRINO's, downloaded on first use at a pinned frcobot_ros2 commit, checked by SHA-256 and cached in the ignored `Simulation/models/fr5/` (they have no license: never commit them). The tube and table body are drawn in the 3D window only, not in the camera's view. Its tests render offscreen at 320 x 180 and use the plain stand-in fish.
- **Tests without ROS:** `Arm/tests/fake_ros.py` is a fake rclpy, move_group (with Pilz's sequence service and its `max_rot_vel` on LIN moves) and FAIRINO command server with message classes built from `ros_messages.json` (the real fields; rebuild with `make_ros_messages.py`). It catches wrong field names and types and logic errors, not what the real MoveIt rejects: that needs `--mode sim` on the robot PC.
- **Tests use their own layout:** `arm_helpers.TEST_LAYOUT` (the placeholder cell in front of the arm, +X), camera mount and look height (`TEST_CAMERA`, `TEST_LOOK_HEIGHT`; `use_test_camera` writes them into a copy of the shipped file) over the shipped workcell file (`make_workcell`, `workcell_data`, `frozen_layout`); ControlSys and Simulation tests put `Arm/tests` on `sys.path` for it. The shipped file is the real cell's (measured, calibrated, turned) and the setup editor and calibration save into it: only tests about the shipped files (`test_the_shipped_layout_works`, the panel test, saving) read it, without its values.

## Conventions

- Comments and docstrings: short and to the point, only what isn't obvious from the code (the why, gotchas, units). No narration.
- User-facing scripts: docstring with a Usage block; every input on the command line, popups for anything missing; print what was done and the next step; `fix_console()` for emoji on Windows consoles.
- **Never destroy user data irreversibly.** Deletions go to `<set>/_deleted/`; ask (or `-y`) before replacing generated output; validate inputs before deleting anything.
- GUIs (tkinter): call `enable_dpi_awareness()` before creating the Tk root; every control gets a `Tooltip`; scale drawing sizes by `self.ui` (display scaling); return focus to the canvas after toolbar commands (`focus_after`), since keys are bound on the window.
- Tests: `Vision/tests/test_data_pipeline.py`, synthetic images and videos, scripts imported with `load_script`; GUI tests use the session `tk_root` fixture and a `Toplevel` per test.

## Gotchas found the hard way

- **Color segmentation fails on the current footage** (white printed fish, reflective gray perforated table): fish and table colors overlap. SAM (`annotating/segmentors/sam.py`) is the auto labeler's default; the color engine needs real color contrast (e.g. dark fish on a light table).
- SAM prompts: points for one object need an extra nesting level (`points=[[p1, p2]], labels=[[1, 0]]`); a flat list makes each point its own object. Each fish's first point is a negative for the other fish, or touching fish merge.
- `cv2.watershed` floods by neighbor color differences, not image brightness, so it can't split by a distance-transform landscape; `ColorSegmentor._split` (`annotating/segmentors/color.py`) uses distance-transform cores.
- pyrealsense2 2.59 records `.db3` (refuses `.bag`) and reads both; 2.55 only `.bag`. Software-device frames reference the NumPy pixel buffer without copying: keep it alive until recording ends.
- Duplicate-frame detection compares color thumbnails: grayscale misses changes between colors of equal brightness.
- `cv2.imread`/`imwrite` fail on non-ASCII paths on Windows: use `pipeline_common.imread`/`imwrite`.
- A second `tk.Tk()` after destroying one can fail on Windows ("Can't find a usable init.tcl"): reuse one root.
- Tk on Windows is blurry at display scaling > 100% unless the process is DPI aware. ttk's clam theme gives buttons a minimum width of 11 characters (`width=0` fixes it). Tk deletes a `tkfont.Font` when Python collects it: keep a reference.
- Albumentations' `MotionBlur` kernels are off-center (up to 2.8 px; 1.5 px with `allow_shifted=False`), moving the picture off its labels: `augment_images.CenteredMotionBlur` makes them point-symmetric. To check for shifts, phase correlation misreads symmetric blurs; use `cv2.matchTemplate`.
- Augmentation is pixel-only on purpose: labels copy byte for byte; geometry is Ultralytics' job at training time. (A spatial effect would need `BORDER_CONSTANT`, `fill_mask=0`: mirrored borders create unlabeled fish.) `PlanckianJitter`'s default range reaches 15000 K (strong blue); we use 4000-7500 K.
- Ultralytics: `settings` is one file per user shared by all projects (`train.py` restores the mlflow setting); downloads land in the working directory (`train.py` changes into `training/` and deletes the `.pt` files a run downloaded); `cache="ram"` isn't deterministic (we use `"disk"`); YOLO26 needs 8.4+.
- MLflow 3 refuses the plain-folder store: use SQLite (needs the full `mlflow` package, not `mlflow-skinny`).
- PyPI's Windows torch is CPU-only, and pip prefers PyPI when it has a newer version than the CUDA index: keep torch/torchvision pinned to versions on the chosen index.
- Dependencies currently resolve to OpenCV 5.0 (`opencv-python` and `opencv-python-headless` at the same version); the pipeline is tested on 4.13 and 5.0.

- The gripper as built is six cups under one vacuum, switched by a solenoid valve on an ESP32 (`firmware/valve_control`, `rfp_arm/valve.py`: lines `ON`/`OFF`/`PULSE <ms>`/`STATUS` at 115200 baud, answers `OK ON`/`OK OFF`/`ERR ...`; the same over HTTP), not the control box valves and vacuum switch of the Requirement Spec (`SuctionGripper`, kept as `driver: controller`). The board can't tell whether the cups hold: only the camera's hold check confirms a hold or sees a drop. Opening the port with DTR/RTS raised restarts the ESP32, and a restart closes the valve, so they are held low. Its Wi-Fi credentials live in the git-ignored `secrets.h`: never put them in a tracked file.
- rclpy messages are strict: an `int` assigned to a `float64` field raises. Convert with `float()` (NumPy scalars too). Ctrl+C raises `ExternalShutdownException` in the executor's thread (`RosLink._spin` ends quietly; the main thread says it).
- The FR5 URDF's last link (`wrist3_link`) has its origin on the j6 axis; the flange face is 100 mm further along z (no flange link). Checked against poses taught on the real arm: the URDF chain plus that offset gives the controller's TCP pose (tool 0) to 0.1 mm, so the controller's base frame is `base_link`, joint directions match, and its rx, ry, rz are roll, pitch, yaw about fixed axes. `tool.tcp` is measured from `wrist3_link`.
- A firm seal needs the cups pressed square onto the fish. Vision fits a plane through the body under the six cups (`fish_list._cup_contact`: each cup's median depth) and the grasp pose's z axis follows it; a spot is preferred only if no cup's lip meets a bump past the bellows' stroke (90th percentile vs median; with `strict_seal_check`, past `cup_lip_conform_m`: off by default, real fish differ from the prints it was tuned on, and the hold check tells whether the cups sealed) and the cups' heights against the plane the cups are pressed onto differ by at most the bellows' stroke (`cup_stroke_m`; straight down if the plane is steeper than 15 deg); no such spot: the first the cups fit on, else the balance point (never a refusal). The median alone hid fins: one cup on a printed fin 25 mm above the body never let the others touch; `GraspSequence._approach` then goes on down in one move at `feel_speed` until `Arm.contact_force` (joint torques through `contact.ContactEstimator`, no force sensor) shows the fish pushing back and the cups have pressed on (`Arm.move_lin(until=)`: polled as the arm moves, which stops where it first says so; the whole path to `feel_max_depth` + `press_distance` is checked first, held short of the table's clearance, `_deepest`). The estimate is a size, zeroed `ZERO_AFTER` into that move (moving steadily: the joints' friction counted in, as it isn't at rest); in 3 mm steps with a settle at each it went stop-go and took seconds. Its thresholds are untested on the arm, and the 3.7 controller (stateless) reports no torques: there the approach is blind. Making one joint compliant needs the controller's impedance mode: only a hook exists (`grasp.press_start_commands`).
- Two orientations that are equal can differ by rounding (trace 2.9999999999999996): take a rotation's axis from its skew part and skip the turn when that is zero, or the result is NaN (`poses.interpolate`).
- A straight carry (Pilz LIN) turns the tool evenly while the base swings unevenly along the line, which drags j6 past its stop half way, even when it turns little end to end; and the point-to-point fallback swings a held 0.9 m stand-in's far end off the table or into the operator's zone. So the carry goes through `GraspPlan.carry_via` (`grasp._carry_via`): poses on the straight way every `CARRY_STEP` (and `CARRY_WRIST_STEP` of wrist turn), each turned so j6 is its share of the way from its planned grasp angle to its planned slot angle (`_aimed`: j6 turns one for one with the tool); where the held fish's ends would leave the table or enter a keep-out zone on that way, by way of the nearest spot where it can turn (`_turning_carry`: straight there as lifted, turned in place, straight on as placed; every pose checked with the fish). `carry_ptp_fallback` stays for the rest. A carry planned again goes on from the stop it was heading for (`GraspSequence._carried`): back to the first, the tool turned the short way. After a failed move a held fish is set down again where it lay (`PUT_BACK_NEAR` of where the cups took it, which can be past the pick area's edge: the cups hold it ahead of its middle), in the pick area or in the placement zone; only there is it the operator's (off its slot: taken away, and its slot used next). Found by the benchmark on the turned cell: 9 carries refused in 20 two-fish scenes.
- The vacuum tube runs into the gripper, so the last joint (j6, +-175 deg by itself) must never wind up: `tool.wrist_range_deg` (the panel; default `WRIST_RANGE_DEG`) is checked on every planned move. j6 has one value per tool angle (its range is under 360 deg), so a plan's only freedom is which tool angles it asks for: the cups either way round (they are symmetric) and, head end unclear, the fish either way into the slot (as vision guessed where the wrist rules allow: with `require_heading: false` such fish are picked, and the way that turned the wrist least placed one of 40 backwards in the benchmark). `plan_grasp`'s rules (`Arm.wrist_angle` predicts j6 with the tool straight down; the tilted approach moves it up to 14 deg): a held fish is turned at most 180 deg (`HELD_TURN`), the wrist inside its range and `WRIST_MARGIN` (10 deg) clear of its ends where a way allows; the empty gripper within 90 deg of the middle (`EMPTY_WRIST`) where the fish allows, which also keeps the camera on the side away from the arm (j6 near +-180 turns it toward the arm); no move turns the wrist more than 180 deg (`WRIST_MOVE`; the joint travel limit is 200): a longer turn to the grasp first turns the wrist back to its middle where it is (`GraspPlan.reset_first`), and so does a longer turn back to an observation pose or a closer look (`PickPlaceCycle._go_to`: a place at one end of the range is up to ~185 deg from the pose); of the ways left, the least turning in all, to the grasp, with the fish to the slot and back to the middle, where the arm returns after every place (its observation pose). Closer looks take the way round nearest the middle too, so the arm doesn't turn round to look and back to grab. Placed, the wrist ends at one of two angles half a turn apart; unless they are near +-90, a fish that must arrive the far way round needs the empty gripper past 90 at the grasp (in the placeholder cell about one known-head fish in six, up to ~150 deg): `check_layout` says so per slot, with the placement heading that would avoid it. Teach observation poses with j6 near 0 (`check_layout`: an error past 90).
- VTK's `get_image_depth()` is minus the distance along the optical axis (z-depth, like the D405), and needs the plotter shown first (`show(auto_close=False)`, also offscreen). A virtual camera inside its own housing mesh sees only the housing: the camera's scene leaves it out.
- A vtkOBBTree over a 100k-triangle mesh takes about a second to build: build it once per model, not per placed fish (`world._locator`).
- **The camera's field of view** is `vision.hfov_deg`: 87 deg by the D405's data sheet (the code default, which tests use), the panel's for the cell (87 on the robot PC; the user once measured ~20% less). Only what can't ask the camera uses it: the layout check, the setup editor, the simulator, the twin before its first frame; vision and the cycle's look heights use the frame's own intrinsics, and a run says once when they differ by more than `LENS_WARNING_DEG` (`_say_lens`; `--mode check` prints both).
- The camera at 450 mm sees 0.85 x 0.48 m of table at 87 deg (0.68 x 0.38 m at 74), so a full-size fish lying anywhere is almost always cut off (0 of 20 in the benchmark): the closer look from 0.62 m holds it. Raised parts fill more of the image (the printed catfish stands 0.29 x its length high with its fins), which is why 0.50 m wasn't enough. The outline is seen at about half the fish's height, not at its top: put its pixels on that plane (`outline_height_share`), or off-center fish shift by centimeters.
- **One look finds the fish:** the search looks from the observation poses in turn until one sees a fish, then the arm goes over it; the shipped layout has one, over the pick area's middle (about 1.2 x 0.7 m from 0.65 m at 87 deg vs a 0.53 x 0.39 m pick area: a fish lying past the view's edge still shows enough of itself to be looked at closer). Two looks left and right, or tilting the camera to look further, only add moves (an oblique view also measures the fish's side: below).
- Mount the camera parallel to the tool. Observation poses and closer looks put the camera straight down, so a tilted mount (`camera.mount` `rpy_deg`) tilts the tool instead, and `wrist_angle_at` can't predict j6 past about 8 deg. Tried with the tool kept vertical and the camera aimed obliquely (removed): the oblique outline takes in the fish's side, so the cups landed 1-2 cm off the body's axis. Benchmark (40 full-size fish): untilted 35 placed, slot error 14.7 mm; roll -10 deg 33 (11 lost seals); +10 deg 34, slot error 17.6 mm, 21% more wrist travel.
- The simulator's `placement: view` lays fish only where an observation pose sees all of them, along the image's long side: the easy case, which hid the problem above. Test with `anywhere`.
- With the gripper as built (TCP 245.8 mm past the tip link) the FR5 reaches 0.675 m from its axis with the tool straight down 0.5 m above the table, where stand-ins are lifted and carried, and 0.87 m at a fish's top. The cups hold a fish ahead of its middle (up to `balance_ahead_share` x its length: 126 mm for stand-ins), so placed, the tool is that far past the slot toward the head (`FishSize.cups_ahead` in `check_layout`). The placeholder's slot 2 at (0.38, 0.60), and an interim (0.28, 0.57) checked without that offset, were out of reach when carrying (now (0.20, 0.57)); one-fish benchmarks never showed it. `lift_height_max` (0.5 m) keeps a carried stand-in (up to 0.21 m tall) clear of others lying on its way, and the layout check uses it: don't lower it to make a layout fit; with nothing on the way the carry is lower by itself (`carry_over_seen`).
- j1 stops at +-175 deg: facing the target, a place behind the arm (bearing near 180 deg plus the posture's offset) is out of reach, so turning a layout toward the back can lose a slot (`check_layout` says so).
- **What vision refuses** (`fish_list.FishLocator._fish`): low confidence, cut off at the image's edge (the cycle looks closer), outside the pick area, no depth anywhere on its body (no guessing its height: the approach would go by it; a hole at the middle alone uses the rest of the body, `MIN_BODY_POINTS`), a top lower than `MIN_FISH_HEIGHT` over the table where the cups go (bad depth: the cups would be sent down to it), and only above the fish type's ranges (two fish seen as one). Too small, too narrow for the cups, a fin under a cup: picked all the same (the user gives the arm only fish big enough; the hold check tells whether the cups sealed). An upper limit must hold the fish however it lies: the stand-in reads 0.17-0.23 m wide (its fins).
- The printed catfish balances 98 mm ahead of its outline's middle (`FishModel.center_of_mass`, the closed mesh's volume centroid): cups at the middle sat outside the (then 140 mm) cup footprint's reach of it. Estimating the balance point from width x height fails on it (its raised tail fin reads as tall), hence the fixed share per fish type.
- A script or scratch file named like a standard-library module (`profile.py`, `operator.py`) in a folder that scripts run from shadows that module for everything imported after it.
- **FAIRINO's ROS 2 driver must match the controller's firmware.** The newest frcobot_ros2's `ros2 run fairino_hardware ros2_cmd_server` is a dispatcher with drivers from 3.8.2 on only: on a 3.7 controller it answers every command `-1` and publishes empty states. The 3.7 tags (`V3.0.0_RobotV3.7.6`...) have the driver itself in `fairino_hardware`. The FR5's URDF kinematics are the same at every tag (only inertias changed).
- **A wrong `table.z` shrank every fish:** the outline's plane and the fish's height were measured from it, so a table 8 cm lower than the file says read every fish ~8% short and 8 cm thin: `geometry_out_of_range` and "the cups don't fit". Vision now measures the table around each fish (depth, `_table_around`), and a run stops when it differs from `table.z` by more than `table_tolerance_m` (above: never into the table).
- **The cup check took the footprint's corners** (100, 50 mm out), which lie outside the round cups: fish the cups fit on were refused. Each cup is now a circle that may reach `cup_overhang_m` past the outline; depth holes under cups (shiny skin) leave the decision to the outline.
- **Real fish are smaller and rounder than the 0.79 m print the limits were made on:** they failed the size limits (now only the top of each range refuses; the cycle's expected length is the range's middle and the layout check plans for its top, so raise the top only for bigger fish) and the lip check, which judged each cup's heights against the six cups' common plane: on a 110 mm wide round body the outer cups' sloping shoulders alone took 5 of the 6 mm a lip was allowed, the D405's noise the rest. A lip is now judged against the plane through its own cup's points (`fish_list._lip_bump`), which still catches a fin. A fish whose head end is unclear is picked too (`require_heading: false`: the cups at its middle, into the slot either way round). The simulation's fish are 0.60 m by default.

## Robot safety (Arm, ControlSys)

Until the software limits are in place, the arm runs only at low speed with someone on the emergency stop. New motions run in simulation, then as a dry run with the vacuum off, then with vacuum or real fish. Say clearly when code moves the real arm, keep motion code out of module level (importing must not move the arm), and remember Ctrl+C doesn't cancel a trajectory the controller accepted. The VLM only chooses among candidates; fixed code owns every motion, safety and retry limit (CS-30).
