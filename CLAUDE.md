# CLAUDE.md

How to work on this repo. Overview: README.md; each subsystem README lists what it owns and its Requirement Spec sections.

## Project

A FAIRINO FR5 arm with a suction gripper picks whole catfish off a table and places them with a uniform heading. **Vision** (RealSense D405, YOLO26 segmentation + pose) finds each fish's pose; **ControlSys** runs the cycle (Qwen3-VL picks the fish, fixed code validates every answer and owns every limit); **Arm** moves (MoveIt 2 with Pilz, frcobot_ros2). Fall 2026 is the design term. Working code: the Vision data pipeline in `Vision/data/`, and a first pick-and-place cycle in the `rfp_*` packages (below) that runs offline and in tests but has not been on the real arm.

Requirement IDs (Requirement Spec, Confluence) use these prefixes in code, docstrings and commits: SY system, VS vision, VD vision data and models, CS control, AS arm, SF safety, IF interfaces, HW/SW platform, HC hardware constraints.

## Environment

- `setup.ps1` / `setup.sh` run `tools/setup_rfp.py` (standard library only: it runs before any environment exists): each step checked first, done only if missing (the conda env `rfp`, Python 3.10, matching ROS 2 Humble on Ubuntu 22.04; it asks pip with a dry run whether anything is missing). `--robot` (robot PC) also installs ROS 2, MoveIt 2, ros2_control, librealsense, dialout and clones frcobot_ros2, with the Python environment a `.venv` on the system Python that sees rclpy. Choosing FAIRINO's hardware package and building it stay by hand.
- **Python 3.10 code only** (no `tomllib`, `except*`, `typing.Self`, ...): the `rfp_*` packages run under ROS's Python.
- Dependencies go in the `pyproject.toml` extras (`vision`, `arm`, `control`, `analysis`, `dev`) **and** in `requirements.txt`, which lists every package explicitly (a test checks it covers every extra) and pins torch/torchvision to the CUDA index.
- ROS 2, MoveIt 2, frcobot_ros2, librealsense and vLLM are system installs on the robot PC. Label Studio needs its own environment (it pins `numpy<2`).
- Development is on Windows (VS Code, PowerShell or Git Bash); the robot PC runs Ubuntu. Keep code cross-platform: `pathlib`, no shell calls, tkinter for GUIs.

## Commands

- `pytest` from the repo root. GUI tests skip without a display, the RealSense test without pyrealsense2, SAM tests without the SAM weights (`RFP_SAM_WEIGHTS` points at a `sam2.1_t.pt`). `test_rfp_*.py` needs the repo installed (`pip install -e .`; the conda env does it).
- `ruff check .` and `ruff format .`: ruff pinned to 0.17.x (`dev` extra; default rules change between minor versions), line length 100 (E501). The pre-commit hook (rev must match the pin) runs both on commit; `.github/workflows/checks.yml` runs them and the light tests (dev extra only) on push.
- Every pipeline script supports `--help`; without arguments it asks for its inputs in popups.

## Vision data pipeline (`Vision/data/`)

| Step | Script | Writes |
|---|---|---|
| 1 | `preprocessing/extract_frames.py` | `dataset/image_sets/<video name>/` |
| 2 | `annotating/auto_labeler.py` (SAM or color engine) and/or Label Studio | `.txt` labels next to the images |
| 3 | `annotating/augment_images.py` (pixel-only effects) | `dataset/image_sets/<set> (augmented)/` |
| 4 | `annotating/label_viewer.py` | fixed labels; deleted pairs go to `<set>/_deleted/` |
| 5 | `preprocessing/train_val_data_splitter.py` | `dataset/train/` (train/val/test) and `data.yaml` |
| 6 | `training/train.py` (settings: `training/fish_seg.yaml`) | `Vision/trained_cv_models/<name>_<model>_<date>_<time>/` |
| Preview | `Vision/tests/model_viewer.py` | `Vision/tests/model_previews/<video> - <model>.mp4` (git-ignored) |

Rules the code depends on:

- **`pipeline_common.py` owns paths, file names, label I/O, image I/O and popups.** Use its helpers (`set_dirs`, `label_index`, `find_label`, `read_label`, `write_label`, `imread`, `imwrite`, `mask_to_polygon`, `ask_*`). The scripts aren't a package; each adds `Vision/data` to `sys.path`.
- **Labels** are YOLO segmentation polygons, normalized 0-1. `read_label` returns non-polygon lines separately (`other`); write them back unchanged. `write_label` cuts polygons at the image edge (`clip_polygon`, joining the crossing points along the edge): YOLO skips images whose labels go past 0-1.
- **Names carry meaning.** Frames: `<video name>_<frame number:06d>.jpg`; videos are named by fish ID and view (`fish012_left.mp4`). Augmented copies: `<original name>__aug<n>-<effect>`. Label Studio's `1a2b3c4d-` label prefix is matched.
- **The split** is 80/10/10 train/val/test (`TRAIN_RATIO`, `TEST_RATIO`), each set cut in blocks of consecutive frames so near-duplicate neighbors don't leak across splits; augmented images go to train only, when their original is in train. The same fish may be in every split (the team decided against splitting by fish, despite VD-70's wording). Keep the block and augmented rules.
- `Vision/data/dataset/classes.txt` is the class list (tracked); the splitter stops if a set's `classes.txt` disagrees.
- **Auto labeler** = `LabelViewer` (`annotating/label_viewer.py`) + click-to-label (`annotating/auto_labeler.py`, engines in `annotating/segmentors/`). The second toolbar row shows the current mode's tools (`edit_tools` / `auto_tools`). New outlines replace labels they overlap by IoU > `REPLACE_IOU`. SAM is freed on engine switch and close.
- **No data in Git.** `.gitignore` ignores `Vision/data/dataset/` except `.py`, `.gitkeep` and `classes.txt`, plus `Vision/trained_cv_models/*` except each run's `weights/best.pt` (tracked: the model the cell runs, ~55 MB each; GitHub warns past 50 MB and refuses past 100 MB), `Vision/data/training/mlflow/` and other `*.pt`. The newest run is found by the date in its name, not file times (a clone's are all the same).
- End-to-end checks: copy `Vision/` to a temp folder and run the scripts there (paths are relative to `pipeline_common.py`, so real data stays untouched).

## Pick and place (`rfp_vision`, `rfp_arm`, `rfp_controlsys`)

`ControlSys/rfp_controlsys/pick_place.py --mode setup | observe | offline | sim3d | sim | check | feel | dry-run | run` (its docstring explains each; `main.py` at the root runs it). Rules the code depends on:

- **Three layers behind interfaces.** `rfp_controlsys.cycle` talks to an `Arm` and a `Gripper` (`rfp_arm/interfaces.py`), a `VisionSystem` and a `FishSelector`. Modes only swap what is behind them (`SimArm`/`MoveItArm`, `SimGripper`/`NoGripper`/the real gripper from `make_gripper`). `rfp_vision` and `rfp_arm` don't import each other; `rfp_controlsys` imports both.
- **ROS only in `moveit_arm.py`, `fairino.py`, `ros_link.py`**, imported inside functions: every other module must import and run without ROS (Windows, CI).
- **Units:** meters and radians in code, 4x4 poses `T_a_b` (frame b in frame a), {B} = MoveIt's `base_link`. YAML files use meters and degrees, logs mm and degrees (IF-11).
- **Point-to-point moves go to joint goals** from the robot model's IK seeded with the present joints (`Chain.ik`; a long swing that one solve can't reach is solved in steps about the base), so the arm keeps its posture and the wrist ends where `Arm.wrist_angle` predicted; MoveIt's own IK (a pose goal) is only the fallback.
- **Every plan is checked in fixed code before it runs** (`safety.check_trajectory`: TCP speed, zones, joint travel, the arm against itself), every target by `Workcell.pose_problem`. Don't add a motion path that skips them.
- **The arm against itself** (`rfp_arm/collision.py`): the FR5's links and the gripper as built as spheres (`Arm/configs/collision_model.yaml`, `tool.collision_model`; `""` turns it off), checked along every planned path and in `layout.reach_joints` (a pose reached only against itself is out of reach). Every point of each mesh is in a sphere, none reaches more than its margin past the body (1 cm; 7 mm for the forearm and wrist 2, which are 19 mm apart wherever the tool points down). `Simulation/make_collision_model.py` makes it from the meshes (it needs FAIRINO's, and pyvista): run it again after changing the gripper (a test checks its hash). Not checked against each other: neighbors at a joint, and pairs whose meshes never came within 1 cm in 20000 random poses (MoveIt's "never in collision"). A path is checked every 1 cm of the way (`collision.STEP`), not only at the plan's own points (Pilz samples every 0.1 s: a few cm at the gripper); a pair touching where a path starts may come apart, not touch again. MoveIt's scene has the gripper as one box (`tool.body`); this check runs on every planned path, the 3D simulator's too (offline mode's `SimArm` plans no joints). A held fish isn't in it.
- **The VLM goes in as a `FishSelector`** (`selector.py`); its answers pass `validate_decision` and the fallback rule already. Don't let a selector reach the arm any other way (CS-30).
- **`control_panel.yaml` (repo root) overrides the three settings files** for everything that loads them (`load_workcell`, both `load_settings`; `panel=None` skips it). Its `run` section holds `pick_place.py`'s command-line defaults. A test checks that the shipped panel changes nothing, so a default changed in one place has to be changed in both.
- **Settings files mirror the dataclass defaults** (`vision.yaml`, `control.yaml`: a test compares them); unknown names are errors. `workcell.yaml` has placeholder values and `verified: false`: the real arm refuses it.
- **Benchmark a change to vision, planning or the cycle** before and after: `python Simulation/benchmark.py [--compare <earlier run>]` runs the real cycle on seeded scenes (full-size stand-ins lying anywhere) and scores it against the simulator's truth (`rfp_sim/benchmark.py`). Give each new behavior a setting that turns it off, so the comparison differs by that alone. A scene's layout and camera noise come from its seed alone. One fish per scene only ever fills slot 1: use `--fish 2` for anything about placing.
- **The layout** (`rfp_arm/layout.py`; `--mode setup` is its 3D editor, `rfp_sim/layout_editor.py`): `check_layout` checks a workcell against what the FR5 model reaches (IK seeded facing each target, elbow up, j6 inside the tube's range, the arm clear of itself; observation poses, the pick area at a fish's top and at the lift height, each slot at the carry and release heights), the camera's views (a fish lying where no view sees any of it) and the fish's ends (off the table, into a keep-out zone). Every mode prints it at the start. `save_layout` writes only the layout's lines, in the control panel where it overrides the file (the heading), keeps `.bak` copies, refuses a layout with `problems()` or one it can't write line by line, reads the files back (anything else changed: restored), and sets a verified cell unverified. The editor is kept to what a person sets by hand: the corners of the table, pick area and placement zone, the slots, quarter turns; the camera's views follow the pick area, the placement zone grows to hold its slots, an added slot goes where a whole fish fits (`free_spot`), and hints about the heading (`Finding.minor`) are printed, not shown. VTK drags a sphere widget parallel to the screen at about the focal point's depth, not the ball's, so a ball trails the mouse (up to 10%): the editor puts each ball where the mouse is on the table (`_under_mouse`).
- **Fish types** (`vision.fish_type`: `stand_in` or `catfish`) hold the size limits and `balance_ahead_share`: the head is heavier, so the cups go that share of the measured length ahead of the outline's middle, toward the head (only with the head end known). `Fish.middle` (`target_pose`) is what the pick area and the slots are about, `Fish.grasp_point` where the cups go; `plan_grasp(..., middle=)` puts the middle on the slot, and `GraspPlan.middle_x` tells the arm (`set_held_fish(length, middle_x)`) so the safety checks put a held fish's ends around its middle, not the cups.
- **Closer looks:** a fish cut off at the image's edge (`out_of_frame`) gets a look centered on it from `observation.close_height`, the image's long side along it (`PickPlaceCycle._look_closer`; `close_looks` per fish). Moving the look toward the end cut off instead (a cut-off outline's middle lies toward the part seen) was tried and removed: no full-size fish more, five small ones fewer. Vision keeps `Fish.seen_at` for rejected fish so the arm knows where to look; the re-check before a grasp (CS-41) is from wherever the chosen fish was seen. A run that ends with fish left says why as the last look saw them.
- **Carry height** (`grasp.low_carry`, `rfp_arm/carry.py`): a rigid fish (vision's fish type says: `stand_in`) is carried at its height under the cups + the dip of leveling tilted cups + `lift_margin`, where nothing lies under its way: the plan sweeps its footprint along the straight carry (turning the short way, Pilz LIN) against every outline of this cycle's looks (`Fish.outline`, in {B}), the fish placed since the zone was last cleared and the exclusion zones, `lift_margin` wide. Anything under the way, or not known (a fish cut off at the image's edge that no other look or slot holds, no look that saw the whole pick area, a fish a failed grasp left off the pick area), or a fish that bends (catfish): as high as before (`high_carry_z`). A carry that can't go straight goes up to that height first (a point-to-point path isn't a line). The benchmark measures from the simulator's truth how far carried fish clear the table and the fish under them (`carry_clearance_mm`).
- **Point-to-point speed:** without a fish `free_ptp_*_scale` (0.30), with one `ptp_*_scale` (0.10), chosen by the arm from `set_held_fish`. Empty moves are mostly the wrist turning, which hardly moves the TCP (at 0.10 a half turn took 10 s); `tcp_speed_max` still slows any plan whose TCP would pass it.
- **Refused plans:** `plan_grasp` refuses a fish where it lies (a fish end into a keep-out zone, the wrist past its range, the approach too steep). Nothing moved, so it counts toward the fish's attempts (vision may measure it otherwise next time) but not toward the cycles failed in a row that pause the run (CS-63): one awkward fish doesn't stop the others.
- **Taught demos** (`rfp_controlsys/demo.py`, files in `Demos/`): joint poses in degrees and `joints` / `line` / `vacuum` / `wait` steps, played through the same `Arm` and `Gripper`. A demo opens the workcell's zones (`demo_workcell`): its poses were reached on the arm when taught. Bare `on` / `off` in YAML are booleans.
- **3D simulation** (`Simulation/rfp_sim`, `--mode sim3d`, needs pyvista): a `VirtualArm`, `VirtualGripper` and `VirtualCamera` behind the real interfaces, so the real cycle and vision run on rendered color and depth. The fish model is `Simulation/models/catfish.3mf`, the gripper `Simulation/models/gripper.stl` (its CAD model through `Simulation/import_gripper.py`, in the tip link frame; both tracked, other models there are ignored). The gripper's measured TCP (`tool.tcp`), cup layout (`cup_rows`, `cup_columns`) and footprint (`cup_footprint_m`, 200 x 100 mm) must match the mesh: a test checks. The FR5's meshes are FAIRINO's, downloaded on first use at a pinned frcobot_ros2 commit, checked by SHA-256 and cached in the ignored `Simulation/models/fr5/` (they have no license: never commit them). The tube and table body are drawn in the 3D window only, not in the camera's view. Its tests render offscreen at 320 x 180 and use the plain stand-in fish.
- **Tests without ROS:** `Arm/tests/fake_ros.py` is a fake rclpy, move_group and FAIRINO command server with message classes built from `ros_messages.json` (the real fields; rebuild with `make_ros_messages.py`). It catches wrong field names and types and logic errors, not what the real MoveIt rejects: that needs `--mode sim` on the robot PC.

## Conventions

- Comments and docstrings: short and to the point, only what isn't obvious from the code (the why, gotchas, units). No narration.
- User-facing scripts: docstring with a Usage block; every input on the command line, popups for anything missing; print what was done and the next step; `fix_console()` for emoji on Windows consoles.
- **Never destroy user data irreversibly.** Deletions go to `<set>/_deleted/`; ask (or `-y`) before replacing generated output; validate inputs before deleting anything.
- GUIs (tkinter): call `enable_dpi_awareness()` before creating the Tk root; every control gets a `Tooltip`; scale drawing sizes by `self.ui` (display scaling); return focus to the canvas after toolbar commands (`focus_after`), since keys are bound on the window.
- Tests: `Vision/tests/test_data_pipeline.py`, synthetic images and videos, scripts imported with `load_script`; GUI tests use the session `tk_root` fixture and a `Toplevel` per test.

## Gotchas found the hard way

- **Color segmentation fails on the current footage** (white printed fish, reflective gray perforated table): fish and table colors overlap. SAM (`annotating/segmentors/sam.py`) is the auto labeler's default; the color engine needs real color contrast (e.g. dark fish on a light table).
- SAM prompts: points for one object need an extra nesting level (`points=[[p1, p2]], labels=[[1, 0]]`); a flat list makes each point its own object. Each fish's first point is a negative for the other fish, or touching fish merge.
- `cv2.watershed` floods by neighbor color differences, not image brightness, so it can't split by a distance-transform landscape; `ColorSegmentor._split` (`annotating/segmentors/color.py`) uses distance-transform cores.
- pyrealsense2 2.59 records `.db3` (refuses `.bag`) and reads both; 2.55 only `.bag`. Software-device frames reference the NumPy pixel buffer without copying: keep it alive until recording ends.
- Duplicate-frame detection compares color thumbnails: grayscale misses changes between colors of equal brightness.
- `cv2.imread`/`imwrite` fail on non-ASCII paths on Windows: use `pipeline_common.imread`/`imwrite`.
- A second `tk.Tk()` after destroying one can fail on Windows ("Can't find a usable init.tcl"): reuse one root.
- Tk on Windows is blurry at display scaling > 100% unless the process is DPI aware. ttk's clam theme gives buttons a minimum width of 11 characters (`width=0` fixes it). Tk deletes a `tkfont.Font` when Python collects it: keep a reference.
- Albumentations' `MotionBlur` kernels are off-center (up to 2.8 px; 1.5 px with `allow_shifted=False`), moving the picture off its labels: `augment_images.CenteredMotionBlur` makes them point-symmetric. To check for shifts, phase correlation misreads symmetric blurs; use `cv2.matchTemplate`.
- Augmentation is pixel-only on purpose: labels copy byte for byte; geometry is Ultralytics' job at training time. (A spatial effect would need `BORDER_CONSTANT`, `fill_mask=0`: mirrored borders create unlabeled fish.) `PlanckianJitter`'s default range reaches 15000 K (strong blue); we use 4000-7500 K.
- Ultralytics: `settings` is one file per user shared by all projects (`train.py` restores the mlflow setting); downloads land in the working directory (`train.py` changes into `training/` and deletes the `.pt` files a run downloaded); `cache="ram"` isn't deterministic (we use `"disk"`); YOLO26 needs 8.4+.
- MLflow 3 refuses the plain-folder store: use SQLite (needs the full `mlflow` package, not `mlflow-skinny`).
- PyPI's Windows torch is CPU-only, and pip prefers PyPI when it has a newer version than the CUDA index: keep torch/torchvision pinned to versions on the chosen index.
- Dependencies currently resolve to OpenCV 5.0 (`opencv-python` and `opencv-python-headless` at the same version); the pipeline is tested on 4.13 and 5.0.

- The gripper as built is six cups under one vacuum, switched by a solenoid valve on an ESP32 (`firmware/valve_control`, `rfp_arm/valve.py`: lines `ON`/`OFF`/`PULSE <ms>`/`STATUS` at 115200 baud, answers `OK ON`/`OK OFF`/`ERR ...`; the same over HTTP), not the control box valves and vacuum switch of the Requirement Spec (`SuctionGripper`, kept as `driver: controller`). The board can't tell whether the cups hold: only the camera's hold check confirms a hold or sees a drop. Opening the port with DTR/RTS raised restarts the ESP32, and a restart closes the valve, so they are held low. Its Wi-Fi credentials live in the git-ignored `secrets.h`: never put them in a tracked file.
- rclpy messages are strict: an `int` assigned to a `float64` field raises. Convert with `float()` (NumPy scalars too).
- The FR5 URDF's last link (`wrist3_link`) has its origin on the j6 axis; the flange face is 100 mm further along z (no flange link). Checked against poses taught on the real arm: the URDF chain plus that offset gives the controller's TCP pose (tool 0) to 0.1 mm, so the controller's base frame is `base_link`, joint directions match, and its rx, ry, rz are roll, pitch, yaw about fixed axes. `tool.tcp` is measured from `wrist3_link`.
- A firm seal needs the cups pressed square onto the fish. Vision fits a plane through the body under the six cups (`fish_list._cup_contact`: each cup's median depth) and the grasp pose's z axis follows it; a spot counts only if each cup's lip meets no fin (90th percentile vs median, `cup_lip_conform_m`) and the cups' heights against the plane the cups are pressed onto differ by at most the bellows' stroke (`cup_stroke_m`; straight down if the plane is steeper than 15 deg). The median alone hid fins: one cup on a printed fin 25 mm above the body never let the others touch; `GraspSequence._approach` then steps down until `Arm.contact_force` (joint torques through `contact.ContactEstimator`, no force sensor) shows the fish pushing back. The estimate is a size, read at rest, zeroed just above the fish; its thresholds are untested on the arm. Making one joint compliant needs the controller's impedance mode: only a hook exists (`grasp.press_start_commands`).
- Two orientations that are equal can differ by rounding (trace 2.9999999999999996): take a rotation's axis from its skew part and skip the turn when that is zero, or the result is NaN (`poses.interpolate`).
- A straight carry (Pilz LIN) turns the tool the short way while the base swings, which can wind j6 into its stop where `plan_grasp`'s chosen turn goes the other way round (same end orientation): `motion.carry_ptp_fallback` (on) then carries point-to-point, which follows the planned j6. Found by the benchmark: 3 of 20 full-size fish were given up after 3 such E_MOTION failures each.
- The vacuum tube runs into the gripper, so the last joint (j6, +-175 deg by itself) must never wind up: `tool.wrist_range_deg` in the workcell file is checked on every planned move. j6 has one value per tool angle (its range is under 360 deg), so a plan's only freedom is which tool angles it asks for: the cups either way round (they are symmetric) and, head end unknown, the fish either way into the slot. `plan_grasp`'s rules (`Arm.wrist_angle` predicts j6 with the tool straight down; the tilted approach moves it up to 14 deg): a held fish is turned at most 180 deg (`HELD_TURN`), the wrist inside its range and `WRIST_MARGIN` (10 deg) clear of its ends where a way allows; the empty gripper within 90 deg of the middle (`EMPTY_WRIST`) where the fish allows, which also keeps the camera on the side away from the arm (j6 near +-180 turns it toward the arm); no move turns the wrist more than 180 deg (`WRIST_MOVE`; the joint travel limit is 200): a longer turn to the grasp first turns the wrist back to its middle where it is (`GraspPlan.reset_first`), and so does a longer turn back to an observation pose or a closer look (`PickPlaceCycle._go_to`: a place at one end of the range is up to ~185 deg from the pose); of the ways left, the least turning in all, to the grasp, with the fish to the slot and back to the middle, where the arm returns after every place (its observation pose). Closer looks take the way round nearest the middle too, so the arm doesn't turn round to look and back to grab. Placed, the wrist ends at one of two angles half a turn apart; unless they are near +-90, a fish that must arrive the far way round needs the empty gripper past 90 at the grasp (in the placeholder cell about one known-head fish in six, up to ~150 deg): `check_layout` says so per slot, with the placement heading that would avoid it. Teach observation poses with j6 near 0 (`check_layout`: an error past 90).
- VTK's `get_image_depth()` is minus the distance along the optical axis (z-depth, like the D405), and needs the plotter shown first (`show(auto_close=False)`, also offscreen). A virtual camera inside its own housing mesh sees only the housing: the camera's scene leaves it out.
- A vtkOBBTree over a 100k-triangle mesh takes about a second to build: build it once per model, not per placed fish (`world._locator`).
- The camera at 450 mm sees 0.85 x 0.50 m of table, so a full-size fish lying anywhere is almost always cut off (0 of 20 in the benchmark): the closer look from 0.62 m holds it. Raised parts fill more of the image (the printed catfish stands 0.29 x its length high with its fins), which is why 0.50 m wasn't enough. The outline is seen at about half the fish's height, not at its top: put its pixels on that plane (`outline_height_share`), or off-center fish shift by centimeters.
- Mount the camera parallel to the tool. Observation poses and closer looks put the camera straight down, so a tilted mount (`camera.mount` `rpy_deg`) tilts the tool instead, and `wrist_angle_at` can't predict j6 past about 8 deg. Tried with the tool kept vertical and the camera aimed obliquely (removed): the oblique outline takes in the fish's side, so the cups landed 1-2 cm off the body's axis. Benchmark (40 full-size fish): untilted 35 placed, slot error 14.7 mm; roll -10 deg 33 (11 lost seals); +10 deg 34, slot error 17.6 mm, 21% more wrist travel.
- The simulator's `placement: view` lays fish only where an observation pose sees all of them, along the image's long side: the easy case, which hid the problem above. Test with `anywhere`.
- With the gripper as built (TCP 245.8 mm past the tip link) the FR5 reaches 0.675 m from its axis with the tool straight down 0.5 m above the table, where stand-ins are lifted and carried, and 0.87 m at a fish's top. The cups hold a fish ahead of its middle (up to `balance_ahead_share` x its length: 126 mm for stand-ins), so placed, the tool is that far past the slot toward the head (`FishSize.cups_ahead` in `check_layout`). The placeholder's slot 2 at (0.38, 0.60), and an interim (0.28, 0.57) checked without that offset, were out of reach when carrying (now (0.20, 0.57)); one-fish benchmarks never showed it. The 0.5 m keeps a carried stand-in (up to 0.21 m tall) clear of others on the table: don't lower it to make a layout fit (the low carry goes lower only where nothing lies under the way, and `check_layout` checks at 0.5 m).
- j1 stops at +-175 deg: facing the target, a place behind the arm (bearing near 180 deg plus the posture's offset) is out of reach, so turning a layout toward the back can lose a slot (`check_layout` says so).
- A size limit must hold the fish however it lies: the stand-in reads 0.17-0.23 m wide (its fins), and the old 0.22 limit refused some whole fish after a closer look while the run reported the first look's `out_of_frame`.
- The printed catfish balances 98 mm ahead of its outline's middle (`FishModel.center_of_mass`, the closed mesh's volume centroid): cups at the middle sat outside the (then 140 mm) cup footprint's reach of it. Estimating the balance point from width x height fails on it (its raised tail fin reads as tall), hence the fixed share per fish type.
- A script or scratch file named like a standard-library module (`profile.py`, `operator.py`) in a folder that scripts run from shadows that module for everything imported after it.

## Robot safety (Arm, ControlSys)

Until the software limits are in place, the arm runs only at low speed with someone on the emergency stop. New motions run in simulation, then as a dry run with the vacuum off, then with vacuum or real fish. Say clearly when code moves the real arm, keep motion code out of module level (importing must not move the arm), and remember Ctrl+C doesn't cancel a trajectory the controller accepted. The VLM only chooses among candidates; fixed code owns every motion, safety and retry limit (CS-30).

## Working with the user

- Commit only when asked.
- Before finishing, run `pytest` and `ruff check`, and say what was and wasn't tested, especially anything that needs hardware (arm, camera, recordings) or a person clicking through a GUI.
